How Windy~Sync works

From the first run to the brief your agent finishes.

StatusWhat you needFirst runConnectPick and moveWhere things landThe briefSecurityCommand line

Status

WindySync is in early development and not released yet. It runs AnySync's engine with Windows on both ends: only Windows PCs are listed and accepted. Working today: device identity and looks, the bus repo, the item catalogue, offers and picks, the encrypted PC to PC stream with resume, placing and the brief, in the window and on the command line. CI tests and builds it on Windows, and a tagged version makes a release with windysync-windows-x64.exe.

What you need

  • Two Windows PCs running WindySync (Windows 10 or 11).
  • One GitHub account, signed in with the GitHub CLI (gh auth login) on both, or a token in WINDYSYNC_TOKEN.
  • The two PCs on the same network, so they can reach each other directly.
  • For the last step, any AI agent you like to read GOAL.md.

First run

WindySync gives the device a random eight digit id and keeps it, the name, the look and a key pair in its own folder: %APPDATA%\windysync. On first use it makes your private bus repo, <login>/windysync-bus, and registers the PC there with its public key.

Connect

On the Connect tab, press Find devices on this account and pick the other PC. Choose to send or to receive; the other device shows the request, and its owner approves or declines. The direction holds for this transfer only.

Pick and move

The sender offers a tree of what it has, grouped by kind. Each item shows where it lands on the new PC. Tick what you want; only those travel, straight between the two devices. Folders rebuilt from source (node_modules, target, .venv, __pycache__ and the like) stay behind. If the connection drops, the receiver asks again for what has not arrived, up to 20 times.

Where things land

Every item has a logical id, like editors/vscode, and its paths under Windows' own folders: %APPDATA%, %LOCALAPPDATA%, %USERPROFILE%. The sender packs each item under its id; the receiver unpacks into a staging folder and moves each part to the same place under its own user, whatever that user is called. Whatever was there is kept next to it as <name>.before-windysync. Each transfer gets a folder at %USERPROFILE%\WindySync\<transfer>, with the lists in lists/.

The brief

When everything is in place, the receiver writes GOAL.md into the transfer folder: every item, where it landed, any problems, a note on what is left to do for each, and, when the user folder has another name, which paths to rewrite. Hand it to the agent you use, for example:

cd $HOME\WindySync\<transfer>; claude "Read GOAL.md in this folder and do what it says."

The lists are in lists\: winget import -i lists\winget.txt brings back what winget installed. Done means every item works, or is in TODO-FOR-YOU.md with steps.

Security

The small things on GitHub (the offer, the picks, the stream key) are sealed boxes to the other device's public key (X25519, XSalsa20-Poly1305). Files go as an XChaCha20-Poly1305 stream under a random key only the two devices know; every frame is authenticated, so a wrong key gets nothing and a cut stream fails instead of ending early.

Command line

windysync                               open the window
windysync --scan                        what this device could send
windysync --give <id> [--only a,b]      ask device <id> to receive, then send
windysync --accept [--only a,b]         approve the request waiting here, then do this side
windysync --id                          this device's id, name and look

--only takes item ids or their starts, as --scan lists them; without it the receiver takes everything offered. A device that doesn't run Windows is refused.
